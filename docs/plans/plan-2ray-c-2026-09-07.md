# 2Ray-C — Implementation-Ready Plan

Source: `docs/plans/2ray-c-brainstorm.md` (requirements-only)
Confidence: 4/5 — scope is small and well-defined; weakest sections are
input-extremes behavior (accepted risk by owner) and movement mapping (resolved).
Date: 2026-09-07 · Branch: `experiment/2ray-c`

## Summary

Ground-up rebuild of the ray-casting playground as **2Ray-C**: two prototypes
(A = TypeScript + Canvas2D + Vite; C = plain JS, no build) with identical
minimal scope — two stacked screens, two free-form positive number inputs
(view angle, ray density), 4 border walls + 1 random wall, WASD movement,
uncapped FPS with counter, monochrome only. Purpose: apples-to-apples stack
comparison before committing to the real 2Ray-C.

## Requirements

### Shared behavior (both prototypes)

- **U-001** — Two stacked screens (top map, bottom ray-cast view)
  - acceptance: Given a running prototype, when the page loads, then the
    viewport is split vertically into a top map panel and a bottom cast panel
  - priority: Must · risk: P2
- **U-002** — Top map rendering: white wall lines, white rays, white circle
  player, black background
  - acceptance: Given the map panel, when it renders, then walls/rays/player
    appear as white on black
  - priority: Must · dependencies: [U-006, U-007] · risk: P2
- **U-003** — Bottom cast view: white vertical columns on black, height driven
  by hit distance
  - acceptance: Given the cast panel, when rays hit walls, then white columns
    render with height inversely proportional to hit distance
  - priority: Must · dependencies: [U-007] · risk: P2
- **U-004** — Exactly two controls as positive-number inputs (NO sliders):
  view angle + ray density
  - acceptance: Given the page, when loaded, then two number inputs exist and
    no sliders are present
  - priority: Must · risk: P2
- **U-005** — No validation/clamping rails on the two inputs
  - acceptance: Given either input, when any positive number is typed, then it
    is applied verbatim (extreme values may freeze rendering — accepted)
  - priority: Must · risk: P1 (see R-01)
- **U-006** — World = 4 border walls (the box)
  - acceptance: Given the map, when rendered, then exactly 4 fixed border walls
    enclose the world
  - priority: Must · risk: P3
- **U-007** — Exactly 1 random interior wall, re-rolled on every page refresh
  - acceptance: Given a refresh, when the page reloads, then a new random
    interior wall appears and the previous one is gone
  - priority: Must · risk: P2
- **U-008** — Movement: W/S forward/back, A/D rotate; no sprint
  - acceptance: Given focus in the page, when W/S/A/D are held, then the player
    moves/rotates accordingly at frame-rate-independent speed (delta-time),
    matching prototype-c, and Shift does nothing extra
  - priority: Must · risk: P2
- **U-009** — FPS counter on screen (white text, implementer-chosen corner)
  - acceptance: Given the running prototype, when one second elapses, then the
    counter updates with the observed frame rate
  - priority: Must · risk: P3
- **U-010** — No FPS cap (uncapped render loop)
  - acceptance: Given the prototype, when running, then no additional throttle
    is applied beyond the browser's rAF/display refresh
  - priority: Must · risk: P3
- **U-011** — Monochrome only: black background, white geometry
  - acceptance: Given any rendered frame, then no color/gradient/texture/effect
    appears beyond white-on-black
  - priority: Must · risk: P2
- **U-012** — Player movement bounded to the world box; no wall-collision
  pushback (descends from A-01 — vetoable)
  - acceptance: Given the player, when moving toward a border, then position is
    clamped at the box edge; walls never push the player
  - priority: Must · risk: P2
- **U-013** — Startup state: angle input 60, density input 2, player centered
  (descends from A-02 — vetoable)
  - acceptance: Given a fresh load, when the app starts, then inputs read
    60 / 2 and the player is centered
  - priority: Must · risk: P3

### Delivery

- **U-101** — Prototype A runs via Vite dev tooling (TypeScript, Canvas2D, no
  runtime deps)
  - acceptance: Given the repo, when `npm install && npm run dev`, then
    prototype A opens and behaves per U-001..U-013
  - priority: Must · risk: P2
- **U-102** — Prototype C runs by direct file open (plain JS, no build, no deps)
  - acceptance: Given the repo, when the HTML file is opened in a browser, then
    prototype C behaves per U-001..U-013
  - priority: Must · risk: P2
- **U-103** — Behavior parity across prototypes
  - acceptance: Given both prototypes, when the same actions are performed in
    both, then renders and reactions match per the parity checklist
  - priority: Must · dependencies: [U-101, U-102] · risk: P2
- **U-104** — Each prototype lives in its own named folder in the repo
  - acceptance: Given the repo, when browsing, then two distinct prototype
    folders are present and independently runnable
  - priority: Should · risk: P3

## Test scenarios

- **TS-001** — Launch A (`npm run dev`): map + cast panels render; inputs and
  WASD respond
- **TS-002** — Launch C (double-click): identical panels, inputs, movement
- **TS-003** — Inputs: angle 60/density 2 → nominal rays+FOV; density 0.5 →
  sparse columns; angle 478 → wide FOV. Extreme density (e.g. 9999) may hang
  the tab — documented, NOT a failure (owner-accepted)
- **TS-004** — Refresh: border walls fixed; random wall position changes;
  exactly 1 random wall
- **TS-005** — WASD: player moves/rotates at frame-rate-independent speed (delta-time); clamped at box; no wall pushback
- **TS-006** — FPS counter updates; uncapped (no artificial throttle)
- **TS-007** — Parity: same scripted actions in A and C, compare visuals + response

## Risks and mitigations

| ID | Severity | Risk | Mitigation |
|---|---|---|---|
| R-01 | P1 | Extreme density input freezes rendering (owner accepted: "shut the browser") | None required; documented expectation |
| R-02 | P2 | npm/network friction for prototype A skews the comparison | Deliberate; DX friction is part of the evaluation |
| R-03 | P2 | Scope drift ("just one more thing") | Out-of-scope list + parity checklist gate |
| R-04 | P3 | Copying p5-era repo files instead of clean-room rewrite muddies comparison | Refer to algorithms only; no file reuse from v1/v2 (C-03) |

## Out of scope

Colors, gradients, textures, shading, post-effects; sliders or any extra
controls; min/max/step validation; wall scale/roundness/collision; catnip,
audio, persistence; inset minimap; touch/mobile; sprint/shift; UI frameworks;
test frameworks; branding/HUD beyond the FPS counter; any control beyond the
two number inputs.
